Claude Code 团队如何做代码评审 · 2026-10-15

文章解读 · 作者 Addy Osmani、Morgan Westlee Lunt、Qing Wang · claude.dev Blog · 2026-10-15 发布 · 阅读约 14 分钟

把「读代码」交给机器，把人的注意力留给风险：PR 翻倍，回滚占比降 40% 以上

Claude 写了 Claude Code 约 90% 的代码。团队没有取消评审，而是把大部分阅读移到机器上，按风险分配人的审批，并重投入「快速发现、快速撤销」。目标是多数 PR 至多一人参与即可合并，同时回滚与事故率不上升。

核心判断：「有没有人读过代码」不是好的代理指标

该问的是：这个变更可能出什么问题，哪一项检查（自动或人工）最适合拦住它。评审从末端关卡变成「边写边查」的持续过程。

为什么必须改：变更量暴涨，人工逐行评审不可行

目标

多数 PR 至多一人参与即合并

那个人可以就是作者；前提是回滚和事故不增加。覆盖 CLI、桌面/网页端与移动端仓库。

度量

人的时间 + 护栏

每 PR 人工批准数（中位数与 P95）、人工评论数、PR 等人的时长；回滚率与事故率作护栏。

为什么要护栏

人的时间包括评审时间和修坏代码的时间。只省下前者、却在后者里花回来，就只是把时间挪了位置。

做法：七层检查叠加，人只看风险处

01

作者本地验证

给 Claude 可运行的检查（测试/构建/截图），让它展示输出；新上下文子代理复审 diff；提 PR 前跑找 bug、精简 diff、端到端校验等内部 skill。

细节

Boris Cherny 估计「给 Claude 验证手段」能让最终结果好 2–3 倍。同类问题反复被标记时，从源头修：skill、lint 规则，或 CLAUDE.md（项目栈、约定、目标与非目标，保持简短）/ REVIEW.md（由 code owner 写，说明该区域什么算失败、限制 nit 数量、列跳过路径、要求给出文件+行号证据、摘要以计数开头）。

02

每个 PR 都有 AI 评审

对照整个仓库和 PR 意图读 diff：是否解决问题、是否契合系统、是否破坏别处；修 bug 时找根因。

细节

多个代理并行找 bug，另一组代理对每条发现投票，足够多认可才发布；纯风格/诊断/清理类被丢弃（过滤器经自家 PR A/B 测试）。评论按严重度排序，标 Important / Nit / Pre-existing。每条都要回应：修复或附理由关闭；代理常在夜间接手修复。仓库可设 Quick / Standard / Deep 三档。超过 1,000 行的 PR 大多有发现，小 PR 大多干净。

03

可阻断的安全评审

bug 评审或安全评审有未关闭发现时 PR 不能合并。

细节

误报通过附简短理由关闭来清除；后续提交修复后发现自动清除。可用开源的 security review GitHub Action 或 /security-review 搭建。

04

阻断式自动检查

lint、类型检查、全平台测试、构建；典型 CLI PR 在人看之前要跑几十项检查。

细节

PR 模板要求写明如何测试、如何撤销；Claude 可代填，但发起变更的人要签字确认。

05

按风险分级的人工审批

由变更本身而非作者决定风险档：低风险可零人工，中风险 1 人，高风险 2 人。

细节

一个分类器判定风险档，另一个分类器判断该变更是否仍需额外的人。owner 列为敏感的路径和任何 CI workflow 文件始终需要人。只有仓库可信作者名单上的人能走轻量路径，其余需第二人批准。代理的批准永远不算人的批准。指挥代理的人算作一名必需评审人。批准只对特定 commit 有效，系统无法担保的新提交（代理推送、手工解冲突的合并）需重新批准。

06

合并队列、开关与灰度

合并队列在应用变更后的 main 上重跑全部检查；新行为先通过 flag 给 Anthropic 员工用。

细节

公开版本先进 latest 渠道，stable 渠道随后跟进。员工的高强度使用常在用户之前暴露回归。

07

快速发现、快速回滚

flag 无需部署即可关闭；每周 on-call 轮值；事故复查会问「本该由哪一层拦住」。

细节

发现坏合并仍依赖作者、on-call 和回滚/事故看板。尚无在指标变化时自动收紧审批的「熔断」，工程师希望在更多代码走零人工合并之前先有它。

第 5 层：风险分级（由变更决定，不由作者决定）

风险示例必需人工批准
低文档、文案、仅内部功能、flag 后的增量改动0（自动评审与安全检查通过即可）
中普通产品改动；缓存、自动更新器、系统提示词等敏感区域1 人
高最高风险代码，以及少数始终要两人的路径2 人

评审器本身也在迭代：先抓真 bug，再减轮次

收敛问题：59% 的反复标记来自旧代码

评审器很少发现新 bug，而是每轮多挖出几个旧的；一个 CLI PR 一夜跑了 50 多轮。现改为同时跟踪 rounds-to-pass 与 recall：

  • 轮次上限：3 轮后评审者请作者退一步，重新考虑方案
  • 前几轮之后只复审新增 diff
  • 标记 bug 的类别，让作者修掉所有实例而不是一行
  • 不重复已发布过的发现

评审器的改进闭环（评测、噪音度量）
  • 事故即评测：收集曾导致事故的历史 PR 及其前向修复与回滚，由熟悉代码的工程师确认每个 bug 及位置，评审者每天跑这套集合。
  • 用人的反应度量噪音：每条评论按「已修复 / 说它错了 / 行为是有意的 / 不重要」归类；另在已知干净的 PR 上跑，统计会诱导有害改动的报告频率。书面优先级：先抓真 bug，其次减少评审轮次。
  • 作者是代理时噪音更贵：人几秒就能忽略 nit，代理会去修，于是多一次提交、多一轮评审。
  • 评审必须收敛：一个 CLI PR 一夜之间经历 50 多轮评审与修复，直到作者叫停。
  • 评审代理还会每晚扫描既有代码，提前发现旧 bug。

人留在哪里：方向、高风险、架构、证据、结果

  • 决定要不要做：方向、品味与范围
  • 评审高风险代码：计费、自动更新器、CI workflow
  • 评审会被他人效仿的架构模式
  • 阅读证据：测试输出、运行的命令与结果、截图、评审发现；说不清检查会漏什么，就要求真正的评审
  • 为结果负责：每个上线的变更都有人负责，无论谁敲的代码
上下文共享与「谁落地谁负责」

共享上下文：没有正式流程，也没人记得住整个代码库。想了解某一块时让 Claude 针对那一片写说明（几分钟、反映当前代码），有人还让 Claude 做可视化小工件。读一行文案改动几乎学不到东西，读将要修改模块的说明能学到很多。默认在公开 Slack 频道工作也有帮助。

You land it, you own it：

  • 变更小，易评审、调试、回滚
  • 一切可逆：flag、回滚、分阶段发布几分钟内撤销多数错误
  • 影响范围决定门槛：代价高的代码配更多人和检查
  • 通过遥测和内部使用快速暴露回归
  • 不是追责：修复者上下文最多；事故复查看的是系统

转向：代理让开工变便宜，有些工作不该落地。频道里有人问「为什么」或给出更简单路线时，作者关闭或重塑 PR；要在线程早期提出，而不是在完成的 PR 上留阻断评论。
